Battery Rush Arena — 발표 대본

게임네트워크기초 중간 프로젝트 발표용 스크립트를 읽기 쉬운 문서형 레이아웃으로 정리한 버전입니다. 발표 순서, 예상 시간, 핵심 기술 포인트를 한 화면에서 빠르게 확인할 수 있도록 구성했습니다.

총 발표 시간: 약 10분 총 15개 슬라이드 권위 서버 + Unity + MySQL
읽기 속도 가이드
한국어 프레젠테이션 기준 분당 약 250자입니다. 각 슬라이드에는 예상 시간을 붙였고, 굵게 표시된 부분은 발표할 때 조금 더 천천히 또렷하게 읽는 구간입니다.

슬라이드 1 — 표지 (Battery Rush Arena)

약 20초

안녕하세요. 게임 네트워크 기초 중간 프로젝트 발표를 맡은 [이름]입니다. 제가 이번에 구현한 프로젝트는 실시간 2인 배틀 게임인 Battery Rush Arena 입니다.

Unity 6000.3.10f1 클라이언트와 C# .NET 10 기반의 서버, 그리고 MySQL 8.x 버전을 연동하여 구축했습니다. 특히 모든 게임 로직을 서버에서 판정하는 권위 서버 아키텍처를 채택하고, 경기 결과를 데이터베이스에 안전하게 저장하도록 설계했습니다.

슬라이드 2 — 목차

약 25초

오늘 발표는 총 10개 섹션으로 구성했습니다. 프로젝트 개요와 시스템 구조를 시작으로, 서버 컴포넌트와 프로토콜 설계를 살펴본 뒤, 실제 게임 로직인 이동, 배터리, 함정 시스템에 대해 설명하겠습니다.

마지막으로 MySQL을 활용한 DB 스키마와 저장 흐름, 그리고 Unity 클라이언트 구조를 정리하며 데모 시연으로 마무리하겠습니다.

슬라이드 3 — 프로젝트 개요

약 50초

이번 프로젝트의 핵심은 권위 서버(Authoritative Server) 방식입니다. Unity 클라이언트는 오직 사용자의 입력만 서버로 보내고, 서버에서 계산된 결과 화면을 렌더링하는 역할만 수행합니다. 모든 판정은 서버에서 일어납니다.

서버는 TCP 포트 7777을 사용하며, bra-spike-v1 이라는 전용 프로토콜 버전을 통해 통신합니다. 매치 시간은 120초로 설정되어 있습니다.

기술 스택으로는 렌더링을 담당하는 Unity, 로직과 DB 관리를 담당하는 .NET 서버, 그리고 전적 저장을 위한 MySQL 8.x를 사용했습니다.

슬라이드 4 — 전체 시스템 구조

약 60초

전체적인 데이터 흐름을 살펴보겠습니다. 클라이언트가 입력 프레임을 전송하면, C# 서버가 이를 받아 게임 상태를 갱신하고 다시 클라이언트로 브로드캐스트합니다. 경기가 종료되면 서버는 MySQL에 데이터를 INSERT 또는 UPSERT 합니다.

통신의 안정성을 위해 7777번 포트를 사용하고, 2초 간격으로 하트비트를 주고받습니다. 또한 30초 동안 응답이 없는 클라이언트는 연결이 끊긴 것으로 간주하는 StaleTimeout 로직을 적용했습니다.

슬라이드 5 — 서버 컴포넌트 구조

약 2분 30초

서버는 총 10개의 핵심 컴포넌트로 역할을 엄격하게 분리했습니다. 각각 어떤 일을 하는지 짚어보겠습니다.

  • Program.cs: 진입점이자 의존성 조립소입니다. 설정 객체와 서비스들을 만들고 host.RunAsync()로 서버를 시작합니다.
  • SpikeServerHost: TCP 7777 포트에서 클라이언트를 수락하고, 모든 메시지 라우팅과 시간 기반 이벤트를 처리하는 서버의 핵심 엔진입니다.
  • ClientSession: 연결 하나당 생성되는 상태 컨테이너입니다. 세션 ID, 플레이어 이름, 소속 룸, 마지막 처리 tick, 마지막 응답 시각을 보관합니다.
  • RoomRegistry: 인메모리 룸 디렉토리입니다. 룸 코드 발급, 참가, 퇴장, 호스트 승계 등을 스레드 안전하게 관리합니다.
  • SpikeRoom: 플레이어 위치, 점수, 배터리, 함정, 효과, 쿨다운 등 한 방의 모든 권위 상태를 담는 객체입니다.
  • LengthPrefixedProtocol: 4바이트 길이 헤더를 붙여 TCP 메시지 경계를 명확히 하고, 쓰기 인터리빙을 막는 네트워크 I/O 창구입니다.
  • ProtocolMessages: 클라이언트와 서버가 주고받는 통신 봉투 클래스입니다. 입력, 룸 스냅샷, 결과, 리더보드 등을 담습니다.
  • MySqlPersistenceService: 매치 결과를 MySQL에 저장하고, 실패 시 재시도하며, 저장 후 리더보드를 읽어옵니다.
  • SpikeServerConfig: 포트, 매치 시간, 배터리 개수, 함정 개수, 쿨타임 같은 서버 상수의 단일 출처입니다.
  • PersistenceModels: 매치 저장 결과와 리더보드 반환에 쓰이는 DTO 묶음입니다.

슬라이드 5.1 — 컴포넌트 통신 흐름도

약 70초

각 컴포넌트의 역할을 파악했으니, 이번엔 이들이 실시간으로 어떻게 연결되어 패킷 하나를 처리하는지 전체 흐름을 보겠습니다.

의존 관계

Program.cs가 SpikeServerHost를 만들고, 그 아래에 RoomRegistry, LengthPrefixedProtocol, MySqlPersistenceService가 연결됩니다. 설정값은 SpikeServerConfig가 공통으로 제공합니다.

입력 패킷 처리 5단계

수신 → 역직렬화 → 라우팅 → 로직 적용 → 브로드캐스트 순서로 흐릅니다. 이 구조 덕분에 어느 단계에서 문제가 생겼는지 빠르게 추적할 수 있습니다.

슬라이드 6 — 프로토콜 설계

약 80초

패킷은 4바이트 BigEndian int32 길이 헤더 뒤에 UTF-8 JSON 페이로드를 붙이는 구조입니다. BigEndian을 사용해 네트워크 바이트 순서를 명시적으로 맞췄고, JSON 본문은 compact 형식으로 전송합니다.

  • SemaphoreSlim(1,1): 동시에 여러 메시지가 같은 스트림에 섞여 쓰이는 인터리빙 현상을 막기 위해 스트림당 쓰기를 직렬화합니다.
  • 대소문자 무감지 JSON 파싱: Unity와 서버 간 필드명 대소문자 차이로 데이터가 비는 문제를 예방합니다.
  • WriteIndented = false: 들여쓰기와 줄바꿈을 제거해 고빈도 패킷의 크기를 줄입니다.

슬라이드 7 — 메시지 타입

약 40초

클라이언트는 hello, 방 생성, 준비 상태, input_frame 등을 포함한 8가지 메시지를 보냅니다.

이에 대해 서버는 수락 여부, 룸 스냅샷, 카운트다운, 효과 변경, 결과, 리더보드 등 16가지 세분화된 메시지로 응답하며 게임 상태를 동기화합니다.

슬라이드 8 — 룸 상태 머신

약 65초

게임의 흐름은 Lobby → Countdown → Active → Ended → Saving → ResultsReady 의 6단계 상태 머신으로 제어됩니다.

두 플레이어가 모두 Ready가 되고 호스트가 시작하면 3초 Countdown 후 120초 Active 상태로 넘어갑니다. 종료 후에는 Saving 상태에서 MySQL 저장을 수행하고, 저장이 끝나면 ResultsReady로 전환합니다.

슬라이드 9 — 게임 로직 ① 이동 & 배터리

약 45초

플레이어는 프레임당 0.75 유닛씩 이동하며, 경기장은 ±7.25 유닛 범위를 가집니다. 스폰 위치는 (-5.1, 0)과 (5.1, 0)입니다.

배터리는 맵에 동시에 3개 유지되며, 반경 0.65 유닛 안으로 접근하면 1점을 얻습니다. 획득된 배터리는 3초 후 서버가 다시 생성합니다.

슬라이드 10 — 게임 로직 ② 함정 & SlowShot

약 45초

맵에는 4개의 함정이 있고, 반경 0.65 유닛 안에 들어오면 0.75초 동안 이동 속도가 70%로 감소합니다.

SlowShot은 사거리 3.5 유닛, 내적값 0.25 이상일 때 적중 판정이 나며, 맞은 상대는 1.25초 동안 이동 속도가 65%로 감소합니다. 쿨타임은 4초이고 서버가 권위적으로 관리합니다.

슬라이드 11 — Input Frame 처리 흐름

약 65초

Unity 클라이언트가 키 입력을 감지하면 이동값과 SlowShot 여부를 담아 SendInputFrameAsync 를 호출합니다. 이 패킷은 LengthPrefixed Protocol로 서버에 전달됩니다.

서버는 플레이어의 마지막 처리 tick과 비교해 중복되거나 오래된 프레임을 거부합니다. 유효한 입력이면 위치, 배터리, 함정, 효과를 갱신하고, 갱신된 전체 상태를 다시 모든 클라이언트에 브로드캐스트합니다.

슬라이드 12 — DB 스키마

약 90초

전적 저장용 데이터베이스는 match_results 와 player_stats 두 테이블로 구성됩니다. 데이터베이스는 utf8mb4 문자셋을 사용해 한국어와 모든 유니코드 문자를 안전하게 저장합니다.

  • match_results: 매치 ID, 종료 시각, 종료 사유, 승자, 플레이어 점수, 원본 JSON payload를 저장합니다.
  • player_stats: 플레이어별 승·무·패, 최고 점수, 총 경기 수, 마지막 플레이 시각을 누적 관리합니다.
두 테이블 쓰기는 하나의 트랜잭션으로 묶입니다. 그래서 매치 기록만 저장되고 통계는 빠지는 식의 불일치를 막을 수 있습니다.

슬라이드 13 — MySQL 저장 흐름

약 65초

저장 프로세스는 7단계로 진행됩니다. 매치 종료 → 결과 payload 생성 → Saving 상태 전환 → 트랜잭션 시작 → 성공 시 COMMIT 또는 실패 시 재시도 → 상위 10명 리더보드 조회 → ResultsReady 상태 전환 순서입니다.

특히 저장 실패 시에는 최대 3회 재시도를 적용해 발표 상황에서도 안정적으로 결과를 남기도록 설계했습니다.

슬라이드 14 — Unity 클라이언트 구조

약 45초

클라이언트는 NetworkSpikeBootstrap → NetworkSpikeApp → NetworkSpikeClient → NetworkSpikeProtocol 의 4개 계층으로 분리되어 있습니다.

NetworkSpikeClient 는 실제 TCP 연결과 ReadLoop, HeartbeatLoop를 담당하고, 서버 메시지는 SynchronizationContext 를 통해 메인 스레드로 안전하게 전달됩니다.

슬라이드 15 — 정리 & 데모 동선

약 30초

정리하자면, 이번 프로젝트는 권위 서버 구조로 로직의 보안성과 일관성을 높였고, TCP + Length-Prefix JSON 으로 안정적인 통신을 구성했습니다. 여기에 6단계 룸 상태 머신과 MySQL 트랜잭션 3회 재시도를 더해 저장 흐름의 안정성도 확보했습니다.

이제 실제 데모에서는 서버 실행 후 두 클라이언트가 접속하고, 배터리를 획득하며 SlowShot을 사용하는 장면을 보여준 뒤, 종료 후 match_results 와 player_stats 에 데이터가 정상 저장되는 것을 확인하겠습니다. 이상으로 발표를 마치겠습니다. 감사합니다.

이 문서는 발표 리허설과 빠른 검토를 위해 반응형 읽기용 페이지로 정리한 버전입니다.
